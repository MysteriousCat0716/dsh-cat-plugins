# 给外部评审：记忆插件「从人的记忆里抄的五步」

> 2026-11-04 20:4x · 仓库 `dsh-cat-ill-remember-you` · 版本 0.8.10 · 204 条测试全过（当天收尾时已到 206，见文末补记）
> 请只挑判据和边界，不用改代码。

## 背景

这是一套本地记忆插件：每轮把用户的话和我的回复按「块」提炼成一条记忆（`kind` / `subject` / `summary` / `text` / `anchors` / `entities`），注入时按锚点、实体、向量取回若干条，注入行里能看出「上次用在什么时候」。

原来的判据只有「锚点×2 + 实体」和时间，不看这条记忆**取回之后有没有被用上**。这轮按人类记忆的五个特征做了改动，全部落地并推送。

## 五条改动

### ① 提取强度（`lib/recall.js`）

- 判据：越常想起的记忆越容易被再想起；但「想起来了」不等于「用上了」。
- 实现：`usageOf(db)` 从 `recall_log` 按 `memory_id` 聚合 `n`（注入次数）与 `u`（`used=1` 次数），只算 `section='recall'`（常驻层不算）。`usedBoost = (u / n) * min(1, n / 3) * 1.5` 加进 `scoreOf`。
- 上限 1.5，低于一次锚点命中（2×weight）的量级，避免「用过一次就永久置顶」。
- 已知风险：`n < 3` 时 confidence 打折，新记忆要积累三次注入才满权重。

### ② 再巩固（`lib/recall.js` / `renderHint`）

- 判据：记忆每次被取回都会带上当时的语境；下次再看到时，应该知道它上次是在什么场合被用上的。
- 实现：`retrieve` 末尾查这批命中里 `used=1` 的最近时间，注入行尾追加「（上次用在 MM-DD HH:mm）」。
- 已知风险：只显示时间，不带当时的语境；真正的再巩固（改写记忆本身）没做。

### ③ 情景压语义（`lib/extract.js` `foldPattern`）

- 判据：同一件事反复说，前几次的细节不该各占一条；说到第三次，应该合成「这件事反复出现」。
- 实现：`insertMemory` 的同话题合并分支，`mentions+1` 后调 `foldPattern`：`mentions >= 3` 且 `summary` 不以「反复出现：」开头时，原地把 `summary` 改成 `反复出现：{原摘要}`，`text` 追加「——同一件事已经提过 N 次」，`anchors` / `entities` 取并集。
- 选择「原地折」而不是「新建 pattern 条」：新建会让同一件事在召回里出现两次。
- 已知风险：这是唯一改写已存数据的一步。判错一次，一条普通记忆会被永久打上「反复出现」前缀。目前只有 `mentions >= 3` 一道阈值，没有回滚机制。

### ④ 遗忘按行为（`lib/forget.js`）

- 判据：想起来了但没用上，等于没想起来；「被取回过」不该重置记忆的年龄。
- 实现：`lastEffective(row, usedAt) = max(usedAt.get(id) ?? 0, row.t)`，`usedAt` 来自 `recall_log WHERE used=1 AND section='recall'`。年龄从「上次真的用上」算，没被用过的从写入时间算。
- `decision` / `preference` 仍不自动降级（`STICKY_KINDS`），`permanent` 永不降。
- 已知风险：一条「说得对但当时没被复述」的记忆可能被误沉；尤其是摘要写得不像一句表态的条目。

### ⑤ 情绪加权（`lib/extract.js` / `lib/recall.js`）

- 判据：难受的时刻是人记得最久的。
- 实现：`retentionOf('emotion')` 从 `'ephemeral'`（7 天降级）改成 `'auto'`（30 天）；`scoreOf` 里 `kind === 'emotion'` 加 0.5。
- 已知风险：情绪词表较宽（`累了|难受|难过|玉玉|失眠|焦虑|撑不住|想你|低落|情绪|抑郁|愧疚|孤独|心疼|想哭|好累|很累|不开心|有点烦`），技术讨论里出现「焦虑」可能误判。

## 另外两处修正

### `classify` 只认用户的话

旧版把用户文本和助手回复拼起来判类：助手回一句「这个决定……」，用户一句「我不喜欢这样」就被判成 `decision`。现在 `classify(userText)`，助手的话不参与分类。`subjectOf` 仍会看助手文本，决定「这条的主语是谁」。

已知风险：可能过窄——「他把我的决定总结成一句话」时，若用户原话没有决定词（例如「好 就这个方案」），`kind` 会落到 `fact`。已补同意词 `就按|按你说的|听你的|依你|就这个|就它`，但覆盖不完整。

### 转发只建指针

用户转来 copilot / 朋友 / B 站评论的长文时，`kind='reference'`，摘要只写「他转来一段话（原文 N 字）：首行」，`text` 不截断（普通记忆截 2000 字）。召回时渲染成「转来的话」，并提示原文去 turns 取。

判据：`^[^\n]{0,24}(copilot|gpt|claude|glm|嘎啦吗|朋友|网友|群友|B站|哔哩|知乎)[^\n]{0,24}(说|回复|评价|发来|提到|看到|的观点|的看法|的话)` 且用户文本 ≥ 120 字。

已知风险：用户自己写的长日记若开头提到「朋友说」也会被当转发。

## 想请评审挑的四个地方

1. **①的加权**：`(u/n) * min(1, n/3) * 1.5` 是否会让「碰巧被用过一次」的记忆长期偏高？有没有更稳的形式（例如按 `u` 的绝对次数而不是比率）？
2. **③的原地改写**：是否应该改成「新条 + `supersedes` + 旧条降级」，而不是改旧条的 `summary` / `text`？
3. **④的误沉风险**：`used=1` 是「回复里出现了该记忆的锚点/实体」，从宽。按这个从宽的 `used` 决定降级，会不会把「对但没提」的记忆沉掉？有没有更好的「用上了」判据？
4. **`kind` 过窄**：`classify` 只认用户的话之后，助手做的技术决定会落到 `fact`。这些决定本来就该在 git 里、不该进记忆库，但「他同意了我的方案」这种块也容易变成 `fact`。是补同意词，还是该单独一个 `agreement` 类？
