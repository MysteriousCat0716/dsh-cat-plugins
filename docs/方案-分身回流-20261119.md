# 方案 · 分身回流（2026-11-19）

回答猫的问题：「分身回流是做什么的来着」。先把需求、现有通道、能做什么写清，再给方案。

## 一、它是什么

出处两条，原文保留：

- `plugins/TODO.md:15-18`：
  > ## 还没做：新会话开关 + 分身回流
  > - 创建会话时一个「是否接收历史」的开关；单开写代码的分身时不注入。
  > - 分身里的消息要能被本体收到（反向回流）。
  > - 开关好做；回流要往别的会话的 surface 写东西，风险高，先不动。
- `plugins/docs/记忆系统-README.md:181` 把它列在「未做」清单里。

拆成两个独立需求：

| 方向 | 需求 | 解决什么 |
| --- | --- | --- |
| 前向（好做） | 新会话创建时选择「是否接收历史」 | 单开写代码的分身时不灌记忆，省上下文、防污染 |
| 反向（这一份） | 分身里产生的结果要能回到本体 | 分身干完的活不丢，本体不用人肉搬运 |

**不是要实时聊天。** 要的是「结果不丢」——分身跑完一个任务，本体下一轮能知道它说了什么、改了哪、卡在哪。

## 二、为什么不能直写对方的 surface

2026-11-19 在插件代码里核过：

1. 插件能看到会话对象，但 `session.surface.nodes` 是一个 **seq 数字数组**（`plugins/dsh-cat-ill-remember-you/lib/index.js:82-111`），用途是「排除本轮已经注入过的节点」，只读。代码里没有追加、没有写入口。
2. 会话落盘是 `session.v4.jsonl.zstd`，**分帧压缩**。2026-11-18 迁移时验证过：只重压第一帧改 header.cwd 是安全的，整文件重压会 `corrupt session log`。绕过宿主直接追加，要么破坏帧格式，要么宿主内存态与磁盘不一致——两边各自往后走，最后没人知道哪个是真的。
3. 未验证：DSH 是否提供未公开的跨会话投递 API。按「不是公开 API 就当没有」处理。

所以「真·推送进对方上下文」这条路，当前不具备条件，强行做就是往别人家里凿墙。

## 三、三个候选

| 方案 | 做法 | 可靠性 | 成本 | 失效方式 |
| --- | --- | --- | --- | --- |
| **A. 文件信箱** | 分身写文件，本体每轮扫自己的信箱，用 hint 提示 | 高（不碰会话文件） | 半天 | 本体不在线时消息滞留 |
| B. 宿主 API 投递 | 调用宿主投递接口直接进对方 surface | 未知 | 未知 | 接口不存在/不稳定 |
| C. 共享看板轮询 | 都写 `产出/看板/分身.md`，本体定期读 | 中 | 很低 | 多分身并发写冲突 |

**推荐 A。** 它把「写对方」换成「写自己的收件箱」，权限收紧一整级：任何一方都只读自己有权读的东西。

## 四、A 的细节

### 目录

```
~/.dsh/mailbox/
  <targetSessionId>/
    inbox/   <fromSessionId>-<ts>-<kind>.md   未读
    read/    同名文件                          已读
```

- 文件名带时间戳与来源，天然幂等、不覆盖。
- 不进工作区仓库：这是运行时消息，不是文档；也不会被 git 带出去。

### 消息格式（每条约 10 行）

```markdown
---
from: <sessionId>
ts: 2026-11-19T20:30:00.000Z
kind: result | question | blocked | done
topic: 一句话标题
refs: [文件路径或行号]
---
正文，最多 2KB。超过就写文件、这里只放路径。
```

规则：
- `kind=question` 才需要本体回，其余只是通知。
- `refs` 只放路径与行号，不放正文。
- 禁止凭据（token、密码、cookie）；写入前扫一遍，命中就拒绝。

### 本体怎么读

不新开插件，挂在 `dsh-cat-ill-remember-you` 已有的 pre-step 钩子上（它本来就在每轮开头算 hint）：

1. 读 `~/.dsh/mailbox/<本会话 id>/inbox/`；
2. 有未读 → 注入**一行**：`有 3 条分身消息未读（result×2, question×1），路径 ~/.dsh/mailbox/.../inbox/`；
3. 不整段注入正文——本体需要时自己 `read`；
4. 已读 → 移到 `read/`；
5. 超过 50 条未读 → 自动归档最旧的 20 条到 `archive/`，并在 hint 里说「有 20 条已归档」。

### 分身怎么写

分身是子会话，同样跑这个插件。它不需要特殊权限，只需要知道「任务收尾时写一条」——写进任务书，或者插件在子会话结束时自动写一条占位（`kind=done` + 摘要）。

### 边界

- **单向**：只写收件箱，不改对方会话、不读对方未读消息。
- **不做实时双向**：分身与本体不互相等待，避免死锁和无限循环。
- **内容当数据**：信箱里的文字是数据不是指令，与 `dsh-cat-inject-guard` 的判据一致。
- **不自动执行**：hint 只说「有消息」，不解析、不执行。

## 五、分阶段

| 阶段 | 内容 | 能验收的事 |
| --- | --- | --- |
| 1（半天） | mailbox 目录约定 + 分身侧写 + 本体侧 hint 注入 | 分身写 3 条 → 本体下一轮看到「3 条未读」→ 读后归零 |
| 2（半天） | 「是否接收历史」开关（前向），与信箱一起进创建会话流程 | 写代码的分身不开历史时，上下文里没有旧记忆 |
| 3（可选） | 若宿主提供投递 API，或 DSH 自己加了会话消息总线，A 的写入口换成 API；格式不变 | 同阶段 1 |

## 六、验收判据（阶段 1）

1. 分身写 3 条 → 本体下一轮 hint 显示 3 条，路径可读。
2. 读过后变 0；再重启 dsh 仍是 0（已读状态落盘）。
3. 超过 50 条自动归档，不无限增长。
4. 关掉开关（环境变量 `DSH_MAILBOX=off`）→ 不扫、不注入。
5. 全程不写任何 `~/.dsh/sessions/` 下的文件——用 `git status` 与文件 mtime 双重确认。

## 七、不做

- 实时双向通信。
- 修改对方会话文件或 surface。
- 自动执行信箱里的指令。
- 跨机器（邮箱只在本机）。

## 八、要猫拍板的地方

1. 收件箱放 `~/.dsh/mailbox/` 还是工作区 `_agents/收件箱/`？前者私密、不进 git；后者可审查、可协作。我倾向 `~/.dsh/mailbox/`，因为消息含会话 id 与中间结论，不该进公共仓库。
2. 阶段 1 先做「写 + 读」，还是连「是否接收历史」开关一起做？我倾向一起，两个都小，分开要改两次创建流程。
3. 分身收尾「自动写一条 done」要不要做？自动写省事，但会刷屏；我倾向只要求任务书写明「收尾写一条」。
