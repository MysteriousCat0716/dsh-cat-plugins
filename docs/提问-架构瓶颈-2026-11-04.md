# 提问：这套记忆接续架构的下一个瓶颈

只读讨论，不改代码，不用逐行审计——前两轮已经审过 `used` 结算、spill 正则、即时通道、persona 污染，这次要结构判断。

## 现在长什么样

宿主是 DSH（DeepSeek Harness）。插件 `dsh-cat-ill-remember-you` 只有一个 SQLite（`~/.dsh/memory/core.db`），零 npm 依赖。

六层：

1. **turns**：每条 user/assistant 原文入库，带 sid/seq/role/origin/cwd/t。
2. **context_stack**：全局栈，只存指针（sid+seq）。容量 50，注入时取最近 20 条，再从剩下 30 条里补最近 10 条本会话的。溢出条目标 `evicted` 并写本地摘要，不删原文。
3. **shadow_v2 / 替换块**：白名单会话（`:full`）里把旧消息压成一条 `[上下文替换｜旧消息压缩，非用户发言]`，用宿主 `surfaceOp:{op:'replace',startSeq,endSeq}` 落地。载体只能是 `user/message`（宿主禁 `assistant/message` 带 `sourceEventSeqs`；`system/message` 要求 source 是 system-prompt）。区间按 surface 节点位置算，节点 0 是 system prompt 不能碰。
4. **memories**：从对话提炼的条目（kind: preference/decision/fact/event，tier: active/dormant/cold，confidence: explicit/reported/uncertain，rule_ver，supersedes 列已加但未接）。
5. **persona**：常驻层，从 mnemon 导入 39 条，按 target 分区、critical 优先、容量 user 4096 / memory 8192 字，每轮注入。
6. **recall**：L1 缓存 → L2 锚点/实体 → L2.4 向量（Ollama qwen3-embedding 0.6b，1024 维，阈值 0.55）→ L2.5 弱匹配 → L3 原文兜底。`recall_log.used` 在 assistant 落库时回填，persona 行不入账。

宿主还给了两个事实：`surfaceOp:replace` 的区间可以覆盖任意节点类型（含 `tool/result`）；但载体的 kind 只能是 user/message 或 node 0 的 system/message。

## 已经修掉的

- persona 行不再写入 `recall_log`（原来每轮最多 8 条挤占 40 条判定窗口）。
- `recall_log (sid, used, id)` 索引。
- spill 路径正则整条换（空格路径、`.txt.bak`、`.TXT`、目录名含 `.txt`）。
- 即时通道：`assistant` 落库时、块完整才提炼，`markConsumed` 同一批 turns，`rule_ver='r1'`。

## 已知缺口

- 替换块只给摘要，没有「按需取原文」的通道（原文在 turns 里，但没有工具/指令让模型主动去取某一段）。
- `supersedes` 列加了，改写/合并还没接（新条目不会替换旧条目，只会并列）。
- 遗忘在数据上是单向的（active→dormant→cold），但被再次取回时 dormant 会回到 active（`reviveOnRecall`）；只剩 cold 单向不回。
- 工具结果可以被区间包进替换块，但替换块本身是 user/message，等于把工具输出伪装成用户发言的一部分。
- 白名单外的会话只注入栈做预览，不改写历史。
- 大输入（一轮几千行）不受替换控制。

## 问四个

1. **下一个最可能先坏的环节是哪个？** 给判据，不要罗列所有可能。我更关心「先坏」而不是「可能坏」。
2. **修的顺序**：上面这些缺口，哪些现在做、哪些可以不做？不做的代价是什么？
3. **验收指标**：`used = 1 / 总注入` 是现在的核心数（低于 30% 说明取回有问题，高于 80% 说明判据太松）。有没有比它更能反映「接续是否真的连续」的指标？
4. **硬条件**：如果要让「完全替换」从白名单测试跑到主会话，还差哪些硬条件（宿主能力、数据完整性、回滚）？
