二、我发现的一个问题
P1 · 诊断归因仍可能错误
文件：tools/eval-diagnose.mjs

岸姐现在仍然这样查找目标的落选记录：
const tr = (hits.trace || []).find(
  (t) => c.want.includes(Number(t.id))
)


问题在于：trace 是整个召回流程的落选账，不只是弱匹配层的落选账。

例如：
1. 目标记忆在 L1 阶段被记录为 no-share。
2. 弱匹配层随后也执行了。
3. 目标记忆进入弱匹配候选池。
4. 诊断脚本发现目标在池里。
5. tr 却取到了前面 L1 留下的 no-share。
6. 最后把它归类为 DROPPED，并报告 no-share。
这就把 L1 的记录错误地当成了弱匹配层的淘汰原因。

更麻烦的是，弱匹配层的 low-weak 记录没有明确写入 section: 'weak'，所以目前不能简单按 section 过滤。

建议： 给 trace 增加明确的 layer 字段，例如：
{
  id: item.id,
  layer: 'weak',
  reason: 'low-weak'
}


其他层也各自标记来源。诊断脚本只读取弱匹配层对应的落选记录。

另外，最好增加一条测试：同一个目标先在 L1 留下落选记录，之后进入弱匹配候选池，验证诊断不会把 L1 的原因误认为弱匹配原因。
三、还有两个小的完善建议
1. SKIPPED 还缺少专门测试。

本轮报告里的 SKIPPED: 0，说明这 12 条用例没有触发跳过情况。

但我们上轮恰恰是在担心跳过时的误判。

建议增加两种测试：
- 前面已经填满两条，弱匹配记录为 budget-full。
- 没有抽出有效词，弱匹配记录为 no-terms。
确保诊断都能正确报告 SKIPPED。

2. vector 层的 ran 语义不够准确。

现在代码在调用 endpointReady() 之前就执行了：
if (vectorRan) ran('vector')


如果 Ollama 实际没有启动，最终仍会记录 vector: ran。

严格来说，这表示尝试执行，而不是成功完成检索。

建议把状态区分为 attempted、completed、failed，或者至少记录失败原因。这不会影响当前弱匹配诊断，但能避免未来评估向量召回时误读日志。
