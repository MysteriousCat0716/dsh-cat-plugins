## 二、pack 层不会被误判成弱匹配淘汰

她担心的是：目标在装盘阶段被 `budget` / `section-cap` 丢掉，诊断会不会把它报成 `DROPPED low-weak`。

不会。`tools/diagnose-core.mjs` 找落选原因时带层过滤：

```js
const traceOf = (layer) => (trace || []).find((t) => t.layer === layer && ids.has(Number(t.id)))
const dropped = traceOf('weak')
```

`pack` 的记录进不了这一条，所以分类是 `GATE`，不是 `DROPPED`。

不过她这一句让我发现原先有个信息丢失：如果是装盘丢的，`GATE` 的说明只写「候选池第 N 位，未进最终」，看不出是「预算满了」还是「没理由地掉出来了」。现在补了一句：

```
GATE  候选池第 3 位，装盘时 budget
```

分类不变（它确实进了池、也没被弱匹配的门槛拒），只是把原因带出来。新增测试「装盘阶段丢的不算弱匹配淘汰，但原因要带出来」盯着这条。

## 三、vector 的 completed 到底意味着什么

她的原话：「completed 必须确实意味着 embedding 成功取得、候选遍历完成，而不能只意味着 endpoint 可用。」

按代码路径核过，现在的 `completed` 只在三种情况落到：

1. `endpointReady` 返回 true（endpoint 在），
2. `embedText` 没抛错（embedding 拿到了），
3. `nearestByVector` 遍历完（不管有没有过 0.55 的门槛，遍历本身完成了）。

对应 `lib/recall.js:636-676`：`endpointReady` 为假直接记 `failed / endpoint-down`，不进后面的分支；`embedText` 抛错被 `catch` 接住，记 `failed / error`；只有走到 `for` 循环末尾才可能是 `completed`。

一个边界要说清：`nearestByVector` 返回空数组时也记 `completed`。我按「遍历完成」理解她的定义，空数组是「查了，没有」，不是「没查成」。如果你认为空结果也该单独标一个状态，我再改。

测试覆盖：新加一条把 endpoint 指到 `127.0.0.1:1`（没人监听），断言 `ran: true`、`status: 'failed'`、`reason` 是 `endpoint-down` 或 `error`。`completed` 那条需要真 Ollama，没测，标未验证。

## 四、各层状态结构统一

她建议「避免某些层只有 ran，另一些层同时有 status」。做了。

现在每一层的形状一样：

```js
{ name, ran, status, reason? }
```

| status | 含义 |
|---|---|
| `skipped` | 没轮到（`reason` 是 `budget-full` / `off` / `cooldown` / `no-terms` / `no-referral`） |
| `attempted` | 轮到它了，还没出结果 |
| `completed` | 这一层跑完了 |
| `failed` | 跑过但没成（向量层的 `endpoint-down` / `error`） |

`ran` 保留，语义只剩「轮到过这一层」。

顺手修了两处记录时机。`weak` 和 `original` 原来在查询之前就记 `ran`，查询本身若是抛错，日志里会留下一条 `completed`。现在两条都挪到查询之后记录（`lib/recall.js:706`、`lib/recall.js:812`）。

还有一条兜底，写在挂 `result.layers` 之前：哪层没写 `status` 就标 `unknown`，不默认填 `completed`。缺字段被读成「跑成了」比标 `unknown` 更坏。

新增测试「每层都有同一个形状」跑一次真检索，断言每层的 `name` 是字符串、`ran` 是布尔、`status` 非空。
