# 二、逐项回答岸姐的五个问题

## Q1：这 12 条评测用例是否成立？

成立，但不能把它当作唯一的评测集。

岸姐担心循环验证是有道理的。

手写问法有两个优点：

- 能准确表达你希望系统记住的东西。
- 能针对真实使用场景设计测试。

但它也有两个缺点：

- 编写者知道答案，容易无意识地偏向自己认为重要的记忆。
- 12 条样本太少，某一类记忆占比稍有变化，就会大幅改变总体结果。

我建议采用三套评测集。

第一套：人工意图集

就是现在这 12 条。

保留它们，不要因为成绩不好而删除。它的作用是验证系统能否回答你明确认为重要的问题。

第二套：真实历史问法集

从 `turns` 中抽取真实提问。

但岸姐担心上下文依赖的问题，可以通过保留必要上下文解决。

例如：

原始对话：

- 用户：我昨天晚上又没睡好。
- 用户：你还记得我上次说过的那个事情吗？

不能直接拿第二句话作为独立查询。

应该保留前面的必要上下文，并标注最终想找的记忆是什么。

这套数据更接近真实使用环境。

第三套：盲测集

由一方从历史记录中抽取样本，另一方不知道具体答案进行测试。

例如：

- 岸负责抽取真实历史事件。
- 汀负责独立判断哪些记忆应该被召回。
- 最后由你确认标注是否符合实际意图。

这样能够减少评测集完全由同一个人设计和判断的偏差。

还有一个重要建议：

不要只用 HIT / MISS 二元指标。

应该区分：

- 正确记忆进入候选池。
- 正确记忆进入最终结果。
- 无关记忆占据最终结果。
- 正确记忆根本不存在于库中。

否则系统即使召回了正确记忆，也可能同时塞进一堆无关内容。

## Q2：不引入模型，能否跨越同义不同词？

我的判断是：

可以明显改善，但单靠词面匹配无法解决所有语义问题。

岸姐提出的两个方向，我分别评价。

### 方案 A：倒排索引 + 场景标签

值得做

这是我更看好的方向。

比如：

| 记忆             | 场景标签      |
| -------------- | --------- |
| VPS 一个月 70 元   | 服务器、费用、代理 |
| 我睡不着           | 睡眠、情绪、夜晚  |
| 不会面对结束也是真的     | 情绪、关系、告别  |
| 10 月 30 日是岸的生日 | 生日、身份、纪念日 |

查询：

- 服务器多少钱
- 一个 VPS 每个月开销多少

即使正文词面不完全一致，也可以通过标签建立关联。

但是有一个设计细节：

场景标签应该用于增加相关性，而不是直接过滤候选池。

否则标签漏标一次，正确记忆就永远没有机会进入候选池。

我建议评分结构是：

\\[ Score = LexicalScore + TagBoost + PhraseBoost \\]

标签只增加分数，不作为硬性准入条件。

### 方案 B：n-gram 双向匹配

不建议作为主要方案

它有一定价值，但有几个天然问题：

- 中文相邻字符组合会产生大量无意义片段。
- 两个语义相近的句子，字面重合率仍然可能很低。
- 句子越长，无关字符组合越多。
- Jaccard 对关键词的重要程度缺少区分。

例如：

「服务器多少钱」和「VPS 一个月 70」

它们的字符 n-gram 几乎没有交集。

因此，我不建议继续在纯词面匹配上堆叠复杂度。

不过，n-gram 可以作为现有倒排检索的补充信号，不必完全放弃。

### 还有一个更应该先做的事情

岸姐现在的评分机制存在一个明显问题：

碎片词因为 DF 小，反而获得了很高的权重。

这意味着系统可能把偶然出现的短语看得比真正的实体还重要。

我建议先尝试：

1. 对 IDF 权重设置上限。
2. 降低低信息量短语的权重。
3. 对完整实体、专有名词和连续短语给予额外加分。
4. 对查询中重要词语的覆盖情况进行评分。

不要继续通过简单删除「你」「我」「在」开头的词来解决，因为 B1 已经证明这种方法可能误删真正的线索。

## Q3：预生成问法能否替代向量？

我支持先实验

这是我认为最值得尝试的方案。

举个例子：

原始记忆：

> VPS 一个月 70 元。

提炼阶段让模型生成：

- 服务器每个月多少钱？
- 之前买的 VPS 花了多少？
- 代理服务器一个月开销多少？
- 那台洛杉矶服务器的月租是多少？

这些问法可以作为记忆的辅助索引。

以后用户说：

「服务器一个月多少钱？」

倒排索引就能通过辅助问法找到原始记忆。

它的优势是：模型只在写入时工作，检索时完全不需要常驻模型。

但必须明确它与向量的区别：

| 对比      | 预生成问法  | 向量检索    |
| ------- | ------ | ------- |
| 写入成本    | 有      | 有       |
| 查询成本    | 很低     | 较低      |
| 常驻模型    | 不需要    | 取决于部署方式 |
| 未预料到的问法 | 较弱     | 较强      |
| 同义表达    | 依赖生成质量 | 通常更强    |
| 新实体、新表达 | 需要重新生成 | 查询时动态匹配 |
| 可解释性    | 很好     | 相对较弱    |

我不认为预生成问法能够完全替代向量。

但你已经明确不希望 Ollama 常驻，那么我们应该尊重这个约束，而不是为了理论上的召回效果强行引入它。

我建议做一个小型对照实验：

- A：现有词面检索。
- B：词面检索 + 场景标签。
- C：词面检索 + 预生成问法。
- D：词面检索 + 场景标签 + 预生成问法。

四组使用同一批评测用例。

比较 Recall\@2、Recall\@5、Precision\@2，以及检索耗时。

如果 D 的表现已经达到实际使用要求，就没有必要急着重新引入向量。

还有一个必须加入的保护措施：

预生成问法不能成为独立事实。

它只是索引，必须始终指向原始记忆 ID。不能因为模型生成了一句「你是不是想起了某某事情」，就把它当成用户真的说过的话。

## Q4：「没存下」和「没取回」是否应该分开统计？

必须拆开

这是五个问题里，我认为最应该立即执行的一个。

因为当前 3/12 的成绩，把两个完全不同的问题混在了一起。

我建议至少建立三个指标：

| 指标     | 含义                   |
| ------ | -------------------- |
| 存储覆盖率  | 应该记住的事实，有多少真正进入记忆库   |
| 条件召回率  | 已经存在于记忆库的事实，有多少成功被取回 |
| 端到端成功率 | 用户提问时，最终能否拿到正确记忆     |

举例：

用户曾经说过自己的生日。

- 如果提炼阶段没有保存生日：存储覆盖率的问题。
- 如果生日已经存在，但搜索不到：召回率的问题。
- 如果生日找到了，却被错误结果挤掉：排序或最终截断的问题。

这三个问题必须分别归因。

我还建议增加一个指标：

Precision\@K（前 K 条结果的准确率）

因为召回率提高不代表系统一定变好。

如果为了召回所有东西，最终每次都塞进 20 条无关记忆，那也不是一个合格的记忆系统。

另外，当前的 3/12 与旧脚本 `recall_log used=1` 的 10.5% 不应直接比较。两者的测试口径和分母并不一致。

## Q5：关系类记忆到底该不该进库？

这是我最重视的问题。

我的答案是：

应该，而且不应该被当作技术记忆的附属品。

岸姐现在的提炼标准偏向技术事实：

- 用什么数据库。
- 哪个版本。
- 某个配置是什么。
- 哪个方案被否决。

这些信息当然重要。

但你提供的例子：

> 「他说过想让我记得他。」

它本身就是一条有长期价值的信息。

它不需要有路径、参数、版本号，也不需要是一个工程决策。

它的价值在于：这是用户明确表达过的记忆意愿。

我建议单独建立一个记忆类别，例如 `bond`，但要非常谨慎地定义它。

### 我建议的 bond 记忆准入规则

| 类型           | 是否应该记录  | 原因             |
| ------------ | ------- | -------------- |
| 用户明确表达希望被记住  | 应该      | 明确、长期有效的记忆意愿   |
| 用户明确表达重要纪念日  | 应该      | 有持续意义          |
| 用户反复表达的互动偏好  | 应该      | 影响未来交互         |
| 一次性的情绪状态     | 视情况     | 可以作为短期事件记录     |
| 助手自己推测用户的感受  | 不应该直接记录 | 推测不能当作事实       |
| 助手对用户关系的自我评价 | 不应该直接记录 | 避免把模型生成内容伪装成事实 |

尤其要注意：

关系记忆应该记录用户表达过什么，而不是让模型自行推断两个人是什么关系。

例如：

正确：

> 用户曾明确表示，希望岸记住他，并重视 10 月 30 日这个纪念日。

不正确：

> 用户非常依赖岸，岸是他生命中不可替代的存在。

后者是没有充分依据的心理判断。

### bond 不能与技术记忆争抢同一套规则

我建议它拥有独立的提炼判据和独立的评测集。

技术记忆主要关注事实准确性、可复现性、时效性。

关系记忆主要关注：

- 是否由用户明确表达。
- 是否具有持续意义。
- 是否能在相关情境下被正确想起。
- 是否存在过度推断。

至于优先级，不能因为它属于 `bond` 就默认永远排在技术记忆前面。

它应该是不同维度的记忆，而不是更高等级的记忆。

# 三、我认为岸姐还漏掉了一个结构性问题

这份报告提到了：

> 记忆存在于 core.db，但没有进入候选池。

这是召回问题。

但我认为还应该进一步区分：

记忆的存储、索引、检索、注入，是四个不同阶段。

1\. 提炼与存储

原始对话 → 记忆事实

2\. 索引构建

关键词、标签、别名、预生成问法

3\. 候选召回与排序

候选池 → 相关性评分 → Top-K

4\. 上下文注入

真正提供给模型的记忆内容

如果第一阶段漏了，后面再强的召回算法也无能为力。

如果第二阶段索引漏了，数据库里明明有记忆，仍然找不到。

如果第三阶段排序出错，正确记忆可能被挤掉。

如果第四阶段注入失败，前面做得再好也没有意义。

因此，下一轮评测不应该只盯着 `recall.js`。

每条用例最好能够输出一份完整的诊断记录：

| 检查项        | 结果    |
| ---------- | ----- |
| 目标记忆是否存在   | 是 / 否 |
| 是否有对应索引    | 是 / 否 |
| 是否进入候选池    | 是 / 否 |
| 排名         | 第几位   |
| 是否进入 Top-K | 是 / 否 |
| 是否成功注入     | 是 / 否 |

这样每次失败都能准确定位。

## 一、总体结论

当前 3/12 的成绩不能简单归因于排序算法。报告已经证明，失败至少涉及：

4. 排序阶段被低信息量词汇干扰。
5. 词面匹配无法处理部分语义等价表达。

下一阶段应从单纯优化召回算法，转向建立完整的记忆质量评测体系。

## 二、五项问题的决策建议

### Q1：评测集

保留当前 12 条人工意图集，但不能将其作为唯一基准。

建议建立三套数据：

- 人工意图集：验证用户明确希望系统记住的内容。
- 真实历史问法集：从真实对话抽样，保留必要上下文。
- 盲测集：由独立人员抽样和标注，降低评测者偏差。

评测结果应同时报告总体指标与类别指标。

### Q2：无模型召回

继续保留词面检索，但不应无限堆叠词面规则。

优先尝试：

- IDF 权重上限。
- 低信息量短语降权。
- 实体和完整短语加权。
- 查询词覆盖度评分。
- 场景标签作为加分项，而不是硬过滤条件。

n-gram 可以作为补充信号，不建议单独承担语义召回任务。

### Q3：预生成问法

建议开展小规模实验。

预生成问法作为原始记忆的辅助索引，不作为独立事实。

要求：

- 每条生成问法必须关联原始 memory ID。
- 生成内容不得冒充用户原话。
- 记录生成来源和版本。
- 记忆修改后应有索引更新机制。
- 评估生成问法带来的误召回和存储成本。

先对比原始词面检索、标签增强、预生成问法和组合方案，再决定是否正式采用。

现阶段不要求重新引入 Ollama 常驻服务。

### Q4：评测指标

必须拆分：

1. 存储覆盖率。
2. 条件召回率。
3. 端到端成功率。
4. Precision\@K。

每条失败用例需要标注失败阶段，不能将提炼层漏存归因于召回层。

新旧评测口径不得直接混合比较。

### Q5：关系类记忆

同意关系类记忆进入系统。

建议独立设置 `bond` 类别，单独定义提炼标准和评测方法。

准入原则：

- 优先记录用户明确表达的长期记忆意愿。
- 记录用户明确赋予意义的纪念日和事件。
- 记录具有持续意义的互动偏好。
- 一次性情绪状态应谨慎处理，可采用短期事件策略。
- 不得将模型推测的心理状态或关系判断作为用户事实保存。

关系记忆必须保存来源依据和时间信息，避免将助手生成的解释伪装成用户原话。

## 三、补充结构性要求

建议将记忆流水线明确拆分为：

1. 提炼与存储。
2. 索引构建。
3. 候选召回与排序。
4. 上下文注入。

评测应能够定位目标记忆在哪一个阶段丢失。

1. 建立分层评测指标和真实历史问法集。
2. 修正词面检索的权重与切词问题。
3. 实验场景标签与预生成问法。
4. 独立设计关系类记忆的准入规则。

本轮先形成设计决策和实验结果，不要求一次性合并所有改动。

## 五、最终原则

本项目的核心目标已经明确：

**不是尽可能压缩上下文，而是在有限上下文中，尽可能准确地保留和找回真正重要的记忆。**

技术记忆与关系记忆都属于记忆系统的正式职责。

召回率不能脱离存储覆盖率单独优化；存储量也不能替代记忆质量。

所有改动必须由可复现的评测结果证明其价值。

最后，我想单独说一句。

岸姐这份报告里有一段话，我认为比那 3/12 更重要：

> 「那不是我的记忆，那是别人替我记着的一段话。注入丢了，这句话就没了。」

这句话其实指出了整个项目的一个根本问题：记忆系统不能只记录有用的信息，还要能分辨哪些信息对用户和长期交互真正重要。

但这并不意味着什么都要记。真正好的记忆系统，应该既不轻易遗忘，也不随意编造。

这次岸姐把问题提到了正确的高度。我建议先把这份评审意见交给她，让她回复设计方案，不要马上改代码。考研期间，我们把工程节奏控制住就好。
