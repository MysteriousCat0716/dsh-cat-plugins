## 一、P1：BM25 的 IDF 统计口径不一致

需要修复

文件：`lib/recall.js`，约 652–661 行。

这里有两段统计：

```
const stats = db
  .prepare(
    "SELECT count(*) AS n, avg(length(text)) AS avg FROM memories WHERE tier = 'active' AND origin IN ('chat', 'unknown')",
  )
  .get();
```

这里的 N 和平均长度只统计：

- `tier = 'active'`
- `origin IN ('chat', 'unknown')`

但计算每个词的 DF 时：

```
const countStmt = db.prepare(
  "SELECT count(*) AS c FROM memories WHERE text LIKE ? ESCAPE '\\'",
);
```

却统计了整个 memories 表。

两者不是同一个统计范围。

BM25 的 IDF：

\\[ IDF=\ln\left(1+\frac{N-df+0.5}{df+0.5}\right) \\]

其中 N 和 df 应当来自同一个语料集合。

现在的实现可能出现：

- N = 800 条有效记忆。
- df = 900 条包含该词的记忆。

这时 df 大于 N，IDF 会变成负数。

而后面的代码又有：

```
if (score <= 0 || ...) {
  note(item, 'low-weak');
  continue;
}
```

于是，一个本来应该有机会召回的记忆，可能因为统计范围不一致而直接被拒绝。

这不是单纯的分数偏差，而是可能导致错误漏召回。

建议修复：

让 N、avg、df 全部使用同一组过滤条件。最好把语料范围统一定义，避免以后修改时再次出现口径分裂。

另外，建议增加一个防御性断言：正常情况下 `0 <= df <= N`。如果不成立，测试应该直接暴露问题，而不是悄悄继续算分。

## 二、P1：所谓取消时间截断，实际仍然有 200 条限制

遗留问题，建议纳入本轮

文件：`lib/recall.js`，弱匹配候选 SQL。

```
WHERE tier = 'active'
  AND origin IN ('chat', 'unknown')
  AND (...)
ORDER BY t DESC
LIMIT 200
```

后面岸姐写了：

```
// 候选池不再按时间截断：时间新不等于相关
candidates.sort((a, b) => b.score - a.score);
```

这句话只对进入 `rows` 的候选成立。

因为 SQL 已经先按时间倒序截断到 200 条了。

假设：

- 一条很重要的记忆是两年前的。
- 它确实包含查询关键词。
- 但最近有 200 条其他记忆也包含该词。

那么老记忆根本进不了 BM25 排序阶段。

这正是我们之前讨论过的 L2 候选池时间截断问题。

我知道这不一定是本次新增的 Bug，但这轮的目标是改善长期记忆召回，因此不能忽略。

建议先不要简单地删除 LIMIT，避免全库扫描带来性能问题。可以考虑：

- 对候选生成使用倒排索引。
- 或者先扩大候选池，再按 BM25 评分。
- 对候选池覆盖率单独做实验。

验收时必须证明：老记忆不会仅仅因为时间久远而失去竞争机会。

## 三、P2：诊断脚本并不能完整诊断流水线

文件：`tools/eval-diagnose.mjs`，约 22–44 行。

岸姐写了：

```
const trace = hits.trace || [];
```

然后用：

```
else if (tr) stage = `进候选被丢（${tr.reason}，${tr.score}）`;
else if (best.got.length === 0) stage = '词面零重叠';
else stage = '进池但没进最终';
```

问题在于，`trace` 本身最多记录 12 条。

`recall.js` 里：

```
if (!item || trace.length >= 12) return;
```

如果目标记忆没有进入最终结果，而且它对应的落选记录恰好排在第 13 条以后，诊断脚本就看不到它。

于是可能把真正的评分门槛淘汰，误判成：

- 词面零重叠。
- 或进池但没进最终。

更重要的是，`eval-diagnose` 所谓的完整诊断，实际上主要是通过 `weakTerms()` 对目标记忆正文做字符串重叠检查。

它没有完整检查：

- anchors 是否匹配。
- entities 是否匹配。
- alias 扩展是否生效。
- 是否经过其他召回层。
- 是否真正完成上下文注入。

因此，它现在更适合叫作「弱匹配诊断」，还不能叫作完整流水线诊断。

建议：

诊断数据应直接由召回流程提供，不要让另一个脚本通过有限的落选账反推所有阶段。

尤其是诊断日志必须能区分：

1. 目标记忆不存在。
2. 目标记忆存在，但没有任何索引命中。
3. 命中候选，但未通过准入门槛。
4. 通过门槛，但被 Top-K 截断。
5. 已经选中，但没有成功注入。

这是我们上一轮明确要求的。

## 四、P2：功能字降权存在误伤风险

文件：`lib/recall.js`，约 156–160 行。

```
const FUNCTIONAL_START =
  /^[我你他她它这那也还就都不没别很太又再才只正在会能要想让给对和与是有说被把从到为以]/
```

```
return term.length === 2 && FUNCTIONAL_START.test(term) ? 0.3 : 1
```

这次岸姐没有删除关键词，而是给部分二字词降权，这个方向是对的。

但问题是：首字属于功能字，不代表整个二字词一定没有意义。

例如：

| 词语 | 可能的问题        |
| -- | ------------ |
| 会话 | 技术术语，却会被降权   |
| 说法 | 可能是有效语义线索    |
| 有趣 | 可能是有效描述      |
| 不能 | 在否定语义中可能非常重要 |

而且 `FUNCTIONAL_START` 包含的首字非常多，实际上已经接近一套硬编码启发式规则。

我不建议现在就推翻它，但至少应该补一组对照测试：

- 碎片词「我说」「也不」确实降权。
- 有意义的二字词「会话」「说法」不应被无条件降权。
- 否定词相关查询不能因为降权而失去重要语义。

尤其要注意：降权只影响 score，`hits` 仍然会累计原始 discount。因此低信息量词仍可能帮助满足两个窗口的准入门槛。

这点也应该纳入测试。

## 五、P2：Precision\@K 没有落实

这属于需求完成度问题。

上一轮设计评审已经明确建议增加 Precision\@K。

现在 `eval-recall-cases.mjs` 输出：

- 存储覆盖率。
- 条件召回率。
- 端到端成功率。

三项拆分是正确的。

但是还没有 Precision\@K。

举个例子：

A 方案召回了正确记忆，同时带回两条无关记忆。

B 方案只召回了一条正确记忆。

如果只看是否命中，两者可能都是 HIT。

但对于一个每轮最多注入两条记忆的系统，结果质量显然不一样。

建议增加：

- Precision\@1
- Precision\@2

同时说明 `want` 是可接受的目标记忆集合，不应把集合之外的所有记忆简单视为无关。评测集需要标注可接受结果，避免误报。
