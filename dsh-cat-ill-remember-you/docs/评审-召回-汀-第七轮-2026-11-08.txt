## 二、我发现的两个新问题

### P1：诊断脚本的候选池与实际召回流程并不完全一致

文件：`tools/eval-diagnose.mjs`

岸姐现在通过重新执行 SQL 来确定目标记忆是否进入候选池。

这个方向比依赖有限 trace 好，但她没有完全复现实际执行条件。

实际 `recall.js` 中，弱匹配层有一个前置条件：

```
if (hits.length < MAX_HITS) {
  // 执行弱匹配候选池查询
}
```

也就是说：

如果前面的召回层已经拿到了两条记忆，弱匹配层根本不会执行。

但是诊断脚本不管这个条件，始终独立执行候选池 SQL。

这会出现这样的情况：

1. 前面的召回层已经填满两个位置。
2. 弱匹配层实际上没有运行。
3. 诊断脚本自己查出目标记忆在前 200 条。
4. 最终把它归类为 `GATE`。

但这条记忆实际上根本没有进入本轮真实执行的弱匹配阶段。

这不是一个准确的失败阶段。

建议：

诊断脚本应明确区分：

- `SKIPPED`：弱匹配层因预算已满而未执行。
- `POOL`：弱匹配层执行了，但目标不在候选池。
- `GATE`：目标确实进入候选池，但被准入条件拒绝。
- `DROPPED`：通过候选阶段，但在后续选择中落选。
- `PICKED`：进入最终结果。
- `ABSENT`：目标记忆不存在。

另外，诊断 SQL 中还有一个小问题：

```
const values = all.map((t) => `%${t}%`)
```

实际 `recall.js` 使用了 `escapeLike(term)`，诊断脚本却没有。

如果关键词包含 `%`、`_` 或反斜杠，诊断查询与真实查询就会产生不同结果。

应统一使用 `escapeLike()`。

### P2：Precision\@K 目前存在统计口径问题

文件：`tools/eval-recall-cases.mjs`

岸姐的代码：

```
const top2 = picked.slice(0, 2)

for (const h of top2) {
  p2den += 1
  if (present.includes(Number(h.id))) p2num += 1
}

if (top2.length && present.includes(Number(top2[0].id))) p1 += 1
```

这里存在两个问题。

第一，`want` 不是完整的相关记忆集合。

岸姐自己也在注释里承认：

> 不在 want 里面的不一定无关。

那么就无法确定不在 `want` 里的结果到底是不是误召回。

因此，目前这个指标只能表示：

- 前 1 条是否命中已标注目标。
- 前 2 条中已标注目标所占比例。

不能严格代表真正的 Precision。

第二，P\@1 和 P\@2 的分母口径不一致。

P\@1 使用：

```
p1 / CASES.length
```

P\@2 使用：

```
p2num / p2den
```

而且 `ABSENT` 的用例会跳过检索，P\@1 却仍然把它算入分母，P\@2 则完全没有相应的返回记录。

这两个数字不能直接并排比较。

建议：

当前阶段可以保留这些数据，但名称改成：

- `TargetHit@1`：第一条是否命中已标注目标。
- `TargetRatio@2`：前两条返回结果中，已标注目标占多少。

同时报告分母。

真正的 Precision\@K，需要先把每条用例的相关记忆标注完整，再计算。

这不是吹毛求疵。我们之前明确要求评测数字必须诚实，不能因为指标名称专业，就让人误以为它代表了尚未验证的东西。
